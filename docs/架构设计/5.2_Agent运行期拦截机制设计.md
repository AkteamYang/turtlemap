# Agent 运行期拦截机制设计

## 1. 文档目标

本文定义 turtlemap os 层已经落地的 Agent 运行期拦截机制（Interceptor）。

这个机制为 Runtime 提供统一的 AOP 扩展边界，在不侵入核心任务调度和状态流转的前提下，对输入、流式消息、事件、工具调用和工具结果实施规范化、校验、修订与治理。

流式文本不应只是由业务侧直接消费的一组 LLM delta。为支持截流、延迟释放、内容修订和覆盖重发，消息发布收敛到 Runtime 统一治理，“流式消息发布拦截与重放机制”作为 Interceptor 的一项专门能力。

## 2. 核心原则

### 2.1 Runtime 持有机制，业务定义策略

这里的分工是：业务代码只实现 `BaseAgentInterceptor` 的职能方法，表达“是否截流”“如何修订”“是否需要重发”等策略。

Runtime、`MessagePublisher` 与 `InterceptorExecutor` 负责：

- 在正确生命周期节点构造动态上下文；
- 串行调用已注册的 interceptor；
- 维护消息流的缓冲状态与事件关联；
- 按既有 event bus 规则发布普通事件、补发事件和覆盖事件；
- 保证事件顺序、`event_id` 关联和结束清理。

业务层不直接构造或发送用于截流释放、内容补发、内容覆盖的底层事件。否则业务需要理解 event bus、collector 与流式协议细节，无法形成可复用且一致的治理能力。

### 2.2 Interceptor 不持有会话运行状态

Interceptor 可以被多个会话或多个 Runtime 使用，因此不将 Agent、SessionState 或任务现场长期保存为 interceptor 自身属性。

Runtime 在每个调用点即时构造 `AgentInterceptorContext`，其中包含：

- 当前 `Agent`；
- 当前 `SessionState`；
- 当前 `ProcessingTask`，在输入尚未建任务的阶段允许为空。

跨多个流式 delta 的状态由 `MessagePublisher` 管理，而不是由业务 interceptor 自行维护。这样可避免并发会话、多个 choice 或消息结束后状态泄漏。

### 2.3 拦截不能改变核心调度语义

Interceptor 只负责修订输入和输出协议，不负责创建任务、切换任务状态、改变 Agent frame、执行工具或自行发布业务事件。

特别地：

- `input_before_process` 只处理外部输入，不创建任务；
- `tool_call_before_execute` 只能修复参数或进行校验，不能将调用改写为另一种工具语义；
- `tool_result_after_execute` 可以规范化展示和错误表达，不得伪造工具执行状态；
- 消息截流只修订展示与上下文两条派生文本通道，不应改写原始文本、tool call、finish reason 等 LLM 协议字段。

### 2.4 每类 hook 明确其组合规则

Interceptor 按 Runtime 注册顺序执行，但不同职能不套用含糊的“都循环一遍”语义：

- 可转换对象的 hook 串行传递，后一个消费前一个的结果；
- 截流判断是保护性约束，任一 interceptor 要求继续截流即保持缓冲；
- 覆盖重发串行传递完整快照；提出重放的 interceptor 可以修订前一个 interceptor 的结果。

通过明确组合规则，多个业务治理能力可以共存，而不会因注册顺序产生难以理解的覆盖关系。

## 3. 模型与职责

```text
Runtime
  ├── interceptors: list[BaseAgentInterceptor]
  └── InterceptorExecutor
        └── 按顺序编排 interceptor hook

OSService
  └── MessagePublisher
        ├── 调用 InterceptorExecutor
        ├── 维护流式截流状态
        └── 向 event bus 发布 MessageEvent
```

### 3.1 BaseAgentInterceptor

`BaseAgentInterceptor` 是所有业务 interceptor 的基础类。它为全部 hook 提供默认实现，因此 Runtime 可以无条件调用，不需要在运行期判断业务类是否实现了某个方法。

`AgentInterceptor` 是 os 层默认扩展类。它当前负责子 Agent `<#CONTINUE#>` 标记的截流、展示通道移除和运行参数写入，同时保留系统内置内容治理的扩展位置。

### 3.2 AgentInterceptorContext

`AgentInterceptorContext` 是单次 hook 调用的动态上下文：

```text
AgentInterceptorContext
    agent: Agent
    session_state: SessionState
    task: ProcessingTask | None
```

它只传递运行期事实，不承载 interceptor 私有状态。输入进入 Runtime 但任务尚未创建时，`task` 为 `None`。

### 3.3 InterceptorExecutor

`InterceptorExecutor` 继承 `BaseAgentInterceptor`，对外保持与 interceptor 一致的方法名称。Runtime 因而只面对一个 interceptor，而执行器在内部完成多 interceptor 编排。

执行器在初始化时校验自己显式重写了基础类的所有公开 hook。基础类以后新增 hook 而执行器未同步时，Runtime 应在初始化阶段失败，避免新 hook 被静默跳过。

### 3.4 MessagePublisher

`MessagePublisher` 是 LLM `MessageEvent` 的唯一发布入口。它不是普通 event bus 的薄包装，而是消息发布状态机：

- 接收消息 `IN_PROGRESS` 与 `END` 事件；
- 按 interceptor 决策截流或释放文本；
- 在 `END` 前补发仍被截流的内容；
- 清理已结束事件的截流状态；
- 发布 `IN_PROGRESS_PARTIAL` 覆盖事件。

## 4. Hook 分类与组合语义

| Hook | 职责 | 组合方式 | 当前调用点 |
| --- | --- | --- | --- |
| `input_before_process` | 输入规范化、特殊字符处理、输入校验 | 串行传递事件列表 | `Runtime.run` 已接入 |
| `message_should_continue_intercept` | 判断当前流式文本是否继续截流 | 任一返回 `True` 即继续；全部 `False` 才释放 | `MessagePublisher` 已接入 |
| `message_before_flush_intercepted` | 释放前修订已截流内容 | 串行传递两条待释放文本与运行参数 | `MessagePublisher` 已接入 |
| `message_build_replay_content` | 决定是否产生覆盖式重发快照 | 串行传递完整快照；所有非空修订都会累积 | `MessagePublisher` 已接入 |
| `event_before_publish` | 补全、校验或规范化公共事件字段 | 串行传递事件 | 接口已定义，尚未接入发布入口 |
| `tool_call_before_execute` | 修复或校验工具调用参数 | 串行传递 tool call | 接口已定义，尚未接入工具执行入口 |
| `tool_result_after_execute` | 规范化工具执行结果 | 串行传递 tool result | 接口已定义，尚未接入工具执行入口 |

### 4.1 输入与工具 hook

输入、事件、工具调用和工具结果属于对象转换型 hook。每一个 interceptor 返回处理后的对象，后一个 interceptor 在该对象基础上继续处理。

适用场景包括：

- 输入中的特殊字符、固定协议字段与格式规范化；
- 事件公共参数校验或展示字段补全；
- 可确定的工具参数修复；
- 工具错误信息、敏感字段和展示文案的统一规范化。

### 4.2 消息 hook

消息 hook 在该设计中分为三个面向流式内容治理的步骤：

1. 是否继续截流；
2. 在释放前如何修订已截流内容；
3. 是否基于完整已接收内容发起覆盖重发。

三者不合并为一个泛化的“消息前置回调”。是否继续截流是状态机决策，释放前修订是内容转换，重发则是对展示层历史内容的显式替换请求，三者对应不同的 Runtime 行为。

## 5. 流式消息发布拦截与重放机制

### 5.1 问题边界

普通流式 SDK 通常把 LLM delta 直接交给调用方。即使业务可以决定丢弃或修改当前 delta，也无法仅靠业务回调可靠处理以下场景：

- 某段文本必须等待后续字符才能判断是否展示；
- 需要把多个 delta 合并后脱敏、修订或移除协议尾标；
- 流式文本已经发送，后续校验发现需要用完整快照覆盖展示内容；
- 同一 completion 存在多个 choice，缓冲状态不能混用；
- 消息结束时仍有尚未释放的内容，必须在 `END` 之前补发。

这些能力都依赖消息发送入口、事件关联和 collector 聚合规则，因此应收敛为 Runtime 的职责，而不要求业务回调自行完成。

### 5.2 截流状态

`MessagePublisher` 按以下逻辑键维护截流状态：

```text
event_id
  └── choice_index
        └── MessageInterceptionContext
```

`MessageInterceptionContext` 包含：

- `chunk_id`、`choice_index`、`chunk_created`、`chunk_model`：用于构造同一消息流的补发 chunk；
- `intercepted_display_content`、`intercepted_context_content`：已接收但尚未释放的展示与上下文文本；
- `received_display_content`、`received_context_content`：当前 choice 已通过释放流程的展示与上下文累计文本；不包含仍在截流中的文本。

provider 原始 `content`、`reasoning_content` 保留为模型输出事实，不再由 interceptor 改写。`MessageModified` 可分别返回 `display_content` 与 `context_content`：`None` 表示该通道不修改；前者只面向用户，后者写入稳定 `LLMMessage` 并在后续模型调用时作为 history。这样展示治理不会意外丢失 Runtime 控制信息，也允许业务明确选择修订范围。

`choice_index` 作为二级键。一个 completion 可以同时产生多个 choice；不同 choice 的截流、释放和重放不能相互污染。

### 5.3 IN_PROGRESS 截流与释放

对于每个 `IN_PROGRESS` choice，按以下流程处理：

1. `MessagePublisher` 为 choice 构建新的截流上下文，并将当前原始 delta 分别合并进两条 intercepted 通道；
2. 若两条 intercepted 通道都没有内容，则跳过该 choice 的 flush、快照合并和重放处理；
3. 当前 chunk 携带 `usage` 时，`is_message_end=True`，不再调用截流判断；`usage` 表示 provider 已确认 completion 结束；
4. 否则调用 `message_should_continue_intercept`；
5. 若继续截流：清空当前 event 的 `display_*` 与 `context_*`，仍发布该 event；原始 delta、tool call、finish reason 等字段保持不变；
6. 若释放：调用 `message_before_flush_intercepted`，将修订后的展示与上下文内容写入当前 event 的派生通道，再发布该 event；
7. 发布前清空 intercepted 通道，并将释放后的内容合并进对应 received 通道；
8. 更新 received 通道后调用 `message_build_replay_content`；若任一 interceptor 返回重放修订，则在当前普通 `IN_PROGRESS` 事件发布后，追加发布同一 `event_id` 的 `IN_PROGRESS_PARTIAL` 覆盖事件。

截流期间仍发送空文本的 `IN_PROGRESS` 事件，以维持既有消息事件生命周期和协议顺序；因此不要求 event bus 或展示层为“截流中”增加专用事件类型。

### 5.4 END 前补发

`END` 事件通常不携带 completion chunk，无法直接承载尚未释放的文本。

当消息进入 `END` 时，`MessagePublisher` 遍历该 `event_id` 下的 choice 截流状态：

1. 对仍有 intercepted 通道内容的 choice 调用 `message_before_flush_intercepted`；
2. 基于已保存的 chunk 与 choice 元信息，将所有待释放 choice 聚合为同一 `event_id` 的一个补发 `IN_PROGRESS` 事件；
3. 先发布该补发事件，再发布原始 `END` 事件；
4. 最后清理该 `event_id` 对应的全部截流状态。

通过该流程，展示层在收到 `END` 时已经拿到本条消息全部允许展示的内容。

### 5.5 覆盖式重放

有些治理无法通过“延迟释放”解决。例如前文已展示，后续校验才发现需要删除、脱敏或统一改写已展示文本。此时 interceptor 可以通过 `message_build_replay_content` 返回新的完整 `MessageContent` 快照。

Runtime 将该快照构造为同一 `event_id` 的 `IN_PROGRESS_PARTIAL` 消息事件。其语义不是新增 delta，而是当前消息内容的完整替换快照：

- `event_id` 与原消息事件一致；
- `choice.index` 与被替换 choice 一致；
- `display_reasoning_content`、`display_content`、`context_reasoning_content` 与 `context_content` 都是截至当前时刻的完整内容；
- collector 遇到 `IN_PROGRESS_PARTIAL` 时覆盖该 choice 已聚合的 display/context 通道，不再追加；原始 `reasoning_content` 与 `content` 不受重放影响；
- 展示层据此替换当前消息的局部内容，而非新建一条消息。

`MessagePublisher` 在每次释放并更新 received 通道后执行 `message_build_replay_content`。返回非空快照时，在当前普通过程事件之后发布 `IN_PROGRESS_PARTIAL`，避免展示层先收到覆盖快照、后收到旧增量。`END` 前补发的释放路径会在 `END` 前发布补发事件和覆盖事件，再发布原始 `END`。

### 5.6 典型场景：隐藏子 Agent 会话标记

子 Agent 可以在最终文本末尾输出 `<#CONTINUE#>`，表示当前会话仍需由该 Agent 继续推进，但不将该控制标记直接展示给用户。

对应 interceptor 只缓冲可能构成标记前缀的尾部文本，处理流程如下：

1. 已截流正文从后向前寻找最后一个 `<`；
2. 若该后缀是 `<#CONTINUE#>` 的合法前缀，则继续截流；
3. 后缀不再可能形成该标记时，释放正文；
4. `usage` 或 `END` 表明消息流结束时，Runtime 通过 `runtime_params` 中的控制信号决定子 Agent 是否退出；
5. 释放前的 hook 从 display 通道移除控制标记，同时在 context 通道保留原始模型信息，用户只看到正常回复。

通过该方式，“模型输出的 Runtime 控制信息”和“面向用户的文本”可以在同一条流中产生，再由 Runtime 在发布边界可靠分离。

## 6. 事件与状态边界

### 6.1 event bus

Interceptor 不替代 event bus。它只在事件进入发布边界前参与处理，最终事件仍由 `ProcessingTask.publish(...)` 通过既有 `event_bus_id` 发送。

普通 `IN_PROGRESS`、补发 `IN_PROGRESS`、`IN_PROGRESS_PARTIAL` 与 `END` 保持同一 `event_id`，并由 event bus 分配各自的顺序号。这样 listener 可以维持按事件顺序消费，collector 也能按稳定事件标识聚合。

### 6.2 Runtime 状态与持久化

`MessageInterceptionContext` 是单次消息流的瞬时发布状态，不写入 SessionState、history 或 checkpoint。

如果 Runtime 在消息流中断前没有收到 `END`，下次运行不恢复该截流缓冲。持久化对象只保存稳定 Runtime 产物，避免把未完成的展示层过程状态误作可恢复的任务事实。

### 6.3 与上下文投影的关系

Interceptor 被限定为“本次输出如何发布”的处理机制，不直接改变会话 history 与 context projection 的所有权模型。

当截流机制修订可展示内容时，稳定 assistant 消息分别保留原始输出、display 通道与 context 通道。后续 history projection 只消费 context 通道；received 通道只用于重放判断。Runtime 如需读取控制信息，应读取原始输出或 `runtime_params`，不从展示事件反推。

## 7. 实现状态与扩展方向

当前已经完成：

- `MessagePublisher` 接入截流、释放、`message_build_replay_content` 与 `IN_PROGRESS_PARTIAL` 覆盖聚合；
- collector 对 `IN_PROGRESS_PARTIAL` 的派生通道执行完整快照覆盖，原始 `content` 与 `reasoning_content` 保持不变；
- os 层默认 `AgentInterceptor` 实现子 Agent `<#CONTINUE#>` 尾标的截流、展示通道移除及 `has_continue_tag` 运行参数写入；
- Runtime 在输入进入 kernel 前调用 `input_before_process`。

后续继续补充：

- 将 `event_before_publish`、`tool_call_before_execute`、`tool_result_after_execute` 接入各自的实际调用点；
- 增加面向生产场景的脱敏、格式规范化、敏感词校验和工具参数修复 interceptor；
- 为拦截器链补充异常策略和可观测性事件，区分 interceptor 自身失败、内容被修订和内容被阻断；
- 覆盖多 choice、空 delta、tool call 与文本混合、`usage` 收尾、END 前释放、覆盖重放等事件序列测试。

## 8. 非目标

该机制明确不承担以下职责：

- 不替代任务系统、handoff、takeover 或 Agent frame 调度；
- 不把所有业务流程都抽象为 interceptor；
- 不允许业务 interceptor 直接操纵 event bus 的事件顺序；
- 不将未稳定的流式缓冲写入 SessionState 或会话 history；
- 不以 interceptor 代替输入鉴权、租户隔离等业务安全边界。
