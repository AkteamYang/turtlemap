# turtlemap 系统架构设计

## 1. 设计哲学

当前 `turtlemap` 系统架构设计遵循以下哲学：

- 技术设计服务于真实问题，而不是概念堆砌
- 向人类自身学习
- 以 `Runtime` 为组织核心
- 可靠信息传达
- 长期运行与可恢复任务现场

这里的含义是：

- 架构设计的价值不在于抽象数量，而在于能否稳定解决 Agent 系统中的真实问题。
- AGI 是人类 AI 发展进程中的重要里程碑，人类自身的行为模式是很好的参考。
- `Runtime` 是组织输入、状态、上下文、工具调用、任务挂起与恢复的核心。
- 只有可靠稳定地获取必要信息，LLM 才可能发挥出最大效果。
- Agent 不应只被理解为一次 prompt + tool 调用，而应被理解为一个持续感知、处理、挂起、恢复和沉淀的运行系统。

更具体地说，`turtlemap` 的核心设计哲学是：以人类行为模式为启发，以 `Runtime` 为组织核心，通过可靠的信息传达、事件驱动输入和可恢复任务现场，最大化 LLM 在长期运行 Agent 系统中的能力释放。

这套哲学会直接指导后续技术实现：

- 因此系统需要 `ObservableEvent`，而不是只接收松散输入字符串。
- 因此系统需要 `BaseProcessingTasks`，而不是只有单一当前消息。
- 因此系统需要区分 `History` 和任务现场，而不是把聊天记录当作全部状态。
- 因此 `ToolResult.content` 要直接面向 LLM 消费，而不是简单透传工具原始输出。
- 因此复杂增强能力应放到外层 `os`，而不是污染 `kernel` 的最小闭环。

## 2. 为什么做 AgentOS

很多时候模型没有做好，并不是模型能力本身不够，而是信息没有被以合适的方式传达到位。这个“信息传达可靠性”问题，应该被当作 AgentOS 的核心工程问题来处理，而不是继续留给开发者个人。

如果进一步回答“为什么要设计 AgentOS”，当前有以下几个核心出发点：

1. 现有 Agent SDK 或 Agent 产品，普遍缺乏标准工程手段来保证信息传递的可靠性，很多能力更多取决于开发者个人调优能力，而不是系统本身的工程能力。
2. 系统构建为无状态但有会话、支持多用户、支持长期运行的 Agent 系统，与偏个人助理形态、偏单体会话形态的产品不同。
3. 决定系统智能水平的核心要素不只是 LLM，还包括 `Knowledge` 和环境感知力；`Runtime` 承载更强的 `Knowledge` 和环境感知能力，并为未来与 LLM 深度融合打基础。

## 3. 系统设计目标

`turtlemap` 整体采用微内核架构，由 `kernel` 与外层 `os` 共同构成。当前总体设计目标是：

- `kernel` 只承载最基础、最稳定、最可复用的原子能力
- 上层能力基于 `kernel` 组合构建，而不是反向侵入内核
- `governance`、应用层通用抽象、场景化编排等能力放在 `kernel` 外层的 `os` 中实现

这样设计的直接目标是：

- 保持内核稳定，避免随着业务场景变化频繁改动
- 保持系统可扩展，允许不同 `os` 形态复用同一套 `kernel`
- 保持边界清晰，让“运行原语”和“系统策略”分层演进

## 4. 系统总体分层

从大框架上看，`turtlemap` 系统当前分为两层：

### kernel

kernel 负责提供 Agent 运行所需的最小闭环原语，包括：

- 对输入的接收与组织
- 对记忆的建模和维护
- 对工具能力的统一描述
- 对推理上下文的基础构建
- 对执行循环的基础控制

### os

`os` 负责在 `kernel` 之上构建真正可运行的 AgentOS 系统能力，包括：

- governance
- 应用层通用抽象
- 场景化工作模式
- 多 Agent 协作
- 编排、路由、策略控制
- 外部系统集成与产品化接口

可以把 `kernel` 看成“最小运行内核”，把 `os` 看成“围绕内核形成的系统层”；两者共同构成 `turtlemap` 的整体系统架构。

## 5. 系统核心交互视角

从交互流程出发，智能体的运行本质上是一个持续循环：

1. 接收输入
2. 结合记忆更新当前处理状态
3. 基于当前状态构建推理上下文
4. 推理得到下一步动作
5. 执行动作并得到结果
6. 继续进入下一轮循环

这里有一个关键前提：

- kernel 不直接面向“客观世界”建模
- kernel 只处理已经进入内核的输入、记忆、工具和运行循环
- 外部环境、事件、交互反馈等信息，进入 kernel 前都应该先被外层系统归一化
- 后续的推理、执行，都是基于内核中的当前状态展开

所以，kernel 的核心不是“理解世界”，而是“以 Runtime 为组织核心，保证最小运行闭环稳定成立”。

## 6. kernel 在系统中的核心对象

在 `turtlemap` 的整体系统架构中，`kernel` 这一层当前可以先围绕以下对象展开。

### 6.1 Input

`Input` 表示已经进入 `kernel` 当前处理范围的输入。

这里强调的是：

- `kernel` 只接收对当前轮次有意义的输入
- 输入在进入 `kernel` 前，可以来自用户、工具结果、handoff 结果、环境变化等不同来源
- 这些输入进入 `kernel` 时，应统一表达为 `ObservableEvent` 这类标准数据结构
- 但这些来源如何采集、如何筛选、如何归一化，不属于 `kernel` 核心职责

换句话说，`kernel` 不关心外层如何形成输入，只关心“现在有哪些 `ObservableEvent` 需要被处理”。

### 6.2 BaseAgentState

`BaseAgentState` 是 kernel 中最核心的主观状态容器。

它不是世界本身，而是 kernel 当前运行所依赖的内部状态。

当前可以先将 Runtime 现场理解为三层：

- `InputQueue / BaseProcessingTask.start_input`
- `SessionState`
- `BaseProcessingTasks`

#### InputQueue / BaseProcessingTask.start_input

`input_queue` 表示尚未被 Runtime 接管的输入集合；`BaseProcessingTask.start_input` 表示启动某个任务时消费的输入包，任务生命周期内固定不变。

这里的关键判断是：

- 外层系统先完成输入归一化
- kernel 再接收这些输入并按任务现场固定起点输入
- `Runtime` 再决定这些输入是恢复某个已有任务，还是创建新的 `BaseProcessingTask`

也就是说，kernel 只需要处理“哪些输入已经进入当前处理范围”，而不需要承担事件系统本身的建模责任。

#### SessionState

表示 Agent 当前会话连续性相关的状态容器。

现阶段可以先分为三层：

- `System`：结构化的系统级定义，当前至少包含 `role`、`objective`、`constraints`、`input_format`、`output_format`、`examples`、`extensions`
- `Knowledge`：分层承载可复用知识，当前至少包括长期记忆、会话摘要、已沉淀的可复用认知
- `History`：面向 LLM 输入构建的最近 `n` 轮用户可见交互记录

其中 `System` 顶层字段应尽量保持少而稳，复杂行为优先收敛在结构化 `constraints` 中；`Knowledge` 内部也应保持分层，例如长期记忆、会话摘要、已沉淀的可复用认知。`History` 只保存后续构建 LLM 输入会使用的最近用户可见交互记录，不保存内部未完成执行过程，也不承担完整审计日志职责。异步任务挂起或任务切换时，如果系统已经向用户形成明确回复，例如“任务异步处理中，处理完成会自动通知您”，这条占位回复应进入 `History`；真实未完成任务现场仍保存在 `BaseProcessingTasks` 中的某个 `BaseProcessingTask`。当前进行中的任务状态不直接进入 `Knowledge`；更全量的审计与展示记录，应由外层 `os` 的独立通道承接。

#### BaseProcessingTasks

表示 Agent 当前会话内未完成任务现场的集合。

它的意义是把“静态状态”和“仍在推进或等待恢复的任务现场”区分开。

当前可以先抽象为若干处理状态类型，例如：

- `MessageState`：承接 assistant message 的增量生成，支持普通 `content` 和 `tool_calls` 两类增量
- `ToolState`：承接整个 tool loop 的运行过程，至少包含已完成消息、执行单元列表和状态字段
- `HandoffState`：承接原 Agent 等待 handoff 完成的任务现场
- `AutoResponseState`：事件触发型自动响应任务，例如定时提醒、天气变化响应等

更合适的表达方式，是用 `BaseProcessingTasks` 持有多个 `BaseProcessingTask`；每个 `BaseProcessingTask` 当前只保留 `task_id` 和 `state` 两个核心属性。`task_id` 用于异步事件回流时查找任务归属；`state` 应继承自统一状态基类，基类提供 `kind` 判别字段和通用生命周期状态，并派生出 `MessageState`、`ToolState`、`HandoffState`、`AutoResponseState` 等具体状态；序列化、反序列化和恢复逻辑都根据 `kind` 分派。`MessageState` 负责 assistant message 的增量生成，完成且结果确认为 `tool_calls` 后，再切换进入 `ToolState`。

这部分的目的不是定义细节状态机，而是明确：

- kernel 需要知道 Agent 现在正在做什么
- 当前尚未完成的过程状态应保留在这里，而不是提前写入 `History`
- 单个 `BaseProcessingTask` 中的“当前处理态”是中断恢复和执行控制的重要基础

### 6.3 Tool

`Tool` 表示 kernel 对外部可调用能力的统一抽象。

kernel 关心的不是某个工具的业务场景，而是工具是否可以被稳定描述、发现、调用和约束。

当前大框架下，`Tool` 至少包含以下几个面向：

- `ToolService`
- `ExecutableTool`
- `ToolMetadata`

#### ToolService

用于提供当前 Agent 维度的工具管理视图。

它承接的不是工具源码扫描或注册中心，而是 `Runtime` 可直接消费的工具对象集合与最小查询入口。

#### ExecutableTool

用于表达 `Runtime` 最终实际调用的完整工具对象。

它至少包括：

- 可序列化的 `ToolMetadata`
- 统一执行入口 `__call__(...)`
- 可选的 `before_execute(...)`

#### ToolMetadata

工具元信息至少分为四层：

- 身份层回答“它是谁”
- 语义层回答“它适合做什么 / 不适合做什么”
- 执行层回答“它怎么被调用”

其中风险语义统一收敛为 `risk_type` 一类字段，并使用带含义的枚举值，而不是简单的高 / 中 / 低等级。执行策略应收敛为 `execution_strategy`，当前先分为 `sync` 和 `async`；异步策略需要提供占位回复入口，用于完成当前轮用户可见交互。权限、重试、熔断、审计等复杂治理能力不进入 `kernel` 基类字段，应由外层 `os` 通过继承 `ToolMetadata` 并重写 `before_execute` 承接。
- 结构层回答“它怎么接收输入”

`tool` 输出在 `kernel` 层统一收敛为 `ToolResult`，其中 `content` 默认作为后续传给 LLM 的 `tool` message 内容。

### 6.4 ContextEngineering

`ContextEngineering` 负责基于当前会话状态、当前 Owner Agent 状态和当前轮可见工具，构建 LLM 推理上下文。

它是 kernel 中连接“状态系统”和“推理系统”的关键桥梁。

当前大框架下，它至少承担以下职责：

- 基于当前状态构建多轮消息
- 将可见工具转成模型可消费的 `tool schema`

这里需要特别强调一个边界：

- kernel 只依赖最小上下文构建接口
- 更复杂的裁剪、压缩、预算控制和提示词治理策略，应当放到 `os` 层

也就是说，kernel 只需要提供“最低限度可运行的上下文工程能力”，而不是承担全部提示词治理责任。

### 6.5 Runtime

`Runtime` 负责 Agent 的基础执行循环。

它的职责不是“决定系统该怎么编排”，而是作为 kernel 的组织核心，保证单个 Agent 运行闭环可以成立。

当前大框架下，`Runtime` 至少包含：

- Agent 执行循环
- 基础流程控制
- 中断与恢复能力

#### 执行循环

执行循环可以先理解为：

- 接收输入与当前状态
- 构建上下文
- 驱动推理
- 产生命令或动作
- 执行动作
- 更新状态并进入下一轮

#### 中断与恢复

中断恢复是 `kernel` 必须具备的基本能力之一。

当前大框架下至少包括：

- `State` 序列化 / 反序列化
- `Resume Context` 重建

它的意义在于保证：

- Agent 可以暂停
- Agent 可以恢复
- 恢复后仍然基于一致的主观状态继续运行

## 7. kernel 核心关系

如果只看对象关系，当前可以先理解为下面这个方向：

```text
External Input
        ↓
Input
        ↓
BaseAgentState
        ↓
ContextEngineering
        ↓
LLM Reasoning
        ↓
Action / Tool Call / Agent Call
        ↓
Runtime State Update
        ↓
Next Loop
```

这个关系里最关键的不是“谁调用谁”，而是下面三点：

- 所有外部信息先在 kernel 外完成归一化
- 所有推理都基于状态层
- 所有执行结果都会进入下一轮状态更新

这意味着 kernel 的核心闭环是一个由 `Runtime` 组织的“输入 -> 状态 -> 上下文 -> 执行 -> 状态”的循环系统。

## 8. kernel 与 OS 的边界

为了避免后续架构失焦，当前明确以下边界。

### 应放在 kernel 的内容

- 输入接收与输入态维护
- 主观状态模型
- 工具统一描述
- 基础上下文工程
- 单 Agent 运行时闭环
- 中断恢复所需的最小能力

### 不应放在 kernel 的内容

- 环境建模
- 事件系统
- 多 Agent 编排
- 复杂规划器
- 策略路由
- 权限治理
- 审计治理
- 场景化流程编排
- 复杂提示词治理策略

### 应放在 OS 的内容

- governance
- 通用应用层抽象
- 环境感知与环境信息注入
- 事件采集与事件归一化
- 输入预处理与 system prompt 注入
- 编排层
- 策略系统
- 多 Agent 协作机制
- 产品化接口与系统集成

## 9. 当前阶段不展开的内容

为了保持大框架阶段聚焦，当前先不进入以下细节：

- 具体类设计
- 具体字段定义
- 具体协议与接口签名
- State 的精确 schema
- Tool 注册 API 细节
- Runtime 状态机细节
- `Knowledge` 的具体存储实现
- Context 压缩算法

当前阶段更重要的是先确认：

- `kernel` 里到底保留哪些最小基础对象
- 这些对象之间的方向关系是什么
- `kernel` 与 `os` 的边界在哪里

## 10. 当前版本结论

当前版本的大框架可以归纳为：

- `turtlemap` 是一个基于微内核思路构建的 AgentOS 系统
- 其中 `kernel` 是最小闭环运行内核，并以 `Runtime` 为组织核心
- `kernel` 围绕 `Input`、`BaseAgentState`、`Tool`、`ContextEngineering`、`Runtime` 五类核心对象展开
- `kernel` 通过“输入 -> 状态 -> 上下文 -> 执行 -> 状态”的循环维持 Agent 的基本运行
- `os` 承载编排、治理和应用层系统抽象等更上层能力
- 两者共同构成 `turtlemap` 的整体系统架构

这套结构的价值在于，后续无论 `turtlemap` 的上层系统能力如何演进，`kernel` 仍然可以保持相对稳定。
