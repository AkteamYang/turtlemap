# 后台压缩任务设计

## 1. 文档目标

本文档用于独立描述 `turtlemap` 中上下文后台压缩任务的工业化设计。

这里的后台压缩特指：当会话历史、记忆或上下文材料逐渐膨胀时，系统在不阻塞当前用户请求的前提下，将旧 `history` 收敛进 `mid_term_memory`，并为后续轮次准备更紧凑、更稳定的上下文材料。

本文档重点回答以下问题：

- 后台压缩应在什么时机触发
- 多进程场景下如何避免重复触发
- 压缩任务基于什么状态执行
- 压缩结果如何安全写回最新状态
- 任务失败、worker 崩溃和租约过期如何处理

## 2. 核心原则

### 2.1 后台压缩是可选治理任务

后台压缩不应被视为当前请求的必要步骤。

也就是说：

- 压缩失败不应影响当前对话继续执行
- 压缩延迟不应阻塞当前 runtime run
- 压缩结果主要服务后续轮次
- 若压缩任务失败，可以标记失败并等待后续轮次重新触发

因此第一阶段不需要在压缩任务模型中加入 `retry_count`。

重试可以由压缩执行器或外部任务系统内部处理；如果最终仍失败，标记任务失败即可。后续新的 runtime run 若仍然判断需要压缩，可以重新创建或抢占过期任务。

### 2.2 后台压缩基于稳定状态快照

后台压缩不应重新构建上下文来判断触发条件，而应复用当前轮已经构建完成的
`ContextBuildResult`。

原因是：

- 上下文构建依赖当前任务、可用工具集合和运行现场；
- checkpoint 后重新构建可能导致工具集合或任务状态变化；
- 后台压缩本身只需要 owner agent state 快照，不需要复制完整 `ContextBuildInput`。

因此当前触发顺序是：

1. `OSService.generate_assistant_message_with_task(...)` 构建本轮上下文并得到 `ContextBuildResult`
2. LLM 生成结束后，复用该 `ContextBuildResult` 判断是否达到软限制
3. 若需要压缩，再尝试创建压缩任务
4. 创建成功后，只复制 `build_input.owner_agent_state` 作为后台压缩输入

后台压缩结果写回时仍会读取最新持久化 SessionState 并做前缀匹配，避免覆盖新的会话进展。

### 2.3 后台压缩必须跨进程可见

工业场景中，一次会话的不同 runtime run 可能被分配到不同进程。

因此不能用当前进程内的 `set[asyncio.Task]` 判断“是否已经触发压缩”。

压缩任务状态必须写入持久化层，并且在触发前读取。

关键要求是：

- 同一 `session_id + agent_name` 在同一时间最多只有一个未过期 running 压缩任务
- 检查 running 任务与写入新 running 任务必须是原子操作
- 正式存储实现应使用事务或唯一约束保证该语义

## 3. 压缩任务状态模型

后台压缩任务模型定义在 `src/turtlemap/os/context/models.py`，不挂在 `SessionState` 中。

最小结构建议如下：

```python
class ContextCompressionTaskRecord:
    """表示一次会话上下文压缩任务的跨进程租约。"""

    # 当前压缩任务的自增主键。
    id: int

    # 当前压缩任务所属会话。
    session_id: str

    # 当前压缩任务所属 Agent。
    agent_name: str

    # 当前压缩任务状态，例如 running / completed / failed。
    status: ContextCompressionTaskStatus

    # 当前租约持有者，用于标识执行该任务的 worker 或进程。
    lease_owner: str | None

    # 当前租约过期时间。
    lease_expires_at: datetime | None

    # 压缩任务失败时的错误说明。
    error: str | None
```

第一阶段可以不加入 `retry_count`。

原因是：

- 后台压缩是可选治理任务
- 压缩失败不会破坏主流程
- 执行器内部可以自行做短期重试
- 最终失败后标记 `failed` 即可
- 后续轮次若仍然需要压缩，可以重新创建新任务

但 `lease_expires_at` 需要保留。

原因是：

- worker 可能在创建任务后崩溃
- 进程内 task 可能永远无法回调完成
- 如果没有租约过期，任务会永久停留在 running
- 后续 runtime run 会一直误判“已有压缩任务在执行”

## 4. 任务创建语义

`StateStoreProtocol` 需要提供一个原子创建压缩任务记录的入口，例如：

```python
async def try_create_context_compression_task(
    self,
    session_state: BaseSessionState,
    agent_name: str,
) -> object | None:
    ...
```

该方法需要保证以下语义：

1. 读取当前会话分支的压缩任务状态
2. 判断同一 `session_id + agent_name` 是否已有未过期的 running 任务
3. 若存在，则返回 `None`
4. 若存在但租约已过期，则刷新原任务的 `lease_owner` / `lease_expires_at`
5. 若不存在，则写入新的 running 任务
6. 返回新创建或被抢占的任务记录

这里的“检查 + 写入”必须是原子操作。

正式数据库实现可选方案：

- 使用事务包裹读取与写入
- 使用 running 唯一槽位限制同一 `session_id + agent_name + running` 任务
- 使用条件更新抢占过期租约

当前 MySQL 与 InMemory 实现均在任务创建时生成 `lease_owner`，调用方不需要传入。
`lease_owner` 使用 `shared.ids.build_executor_instance_id()` 生成，格式为
`hostname:短 uuid`，表示一次具体执行尝试。任务完成时必须携带创建时返回的 `ContextCompressionTaskRecord`，存储层用 `id + lease_owner` 匹配，避免旧 worker 完成已经被抢占的新任务。

当前 MySQL 表通过生成列 `running_task_key` 实现“只有 running 任务唯一”：

```sql
running_task_key =
    CASE
        WHEN status = 'running'
        THEN CONCAT(session_id, '-', agent_name)
        ELSE NULL
    END
```

唯一键建立在 `running_task_key` 上。MySQL unique 允许多条 `NULL`，因此 `completed` / `failed` 记录可以保留多条历史；只有 `running` 状态会占用唯一槽位。任务完成后 `status` 更新为 `completed`，`running_task_key` 会自动变为 `NULL`，后续可以再次创建新的 running 压缩任务。

## 5. 压缩执行流程

当前实现创建任务成功后，会从 `ContextBuildInput` 中只复制 `owner_agent_state` 快照作为压缩输入，避免复制完整构建输入对象。压缩完成后通过回调回到 `OSService`，由回调读取最新持久化 `SessionState` 并尝试合并。

当前流程是：

1. 根据 `session_id + agent_name` 原子创建或抢占压缩任务
2. 只 `deepcopy(build_input.owner_agent_state)` 作为后台压缩快照
3. 记录压缩开始时的 `origin_history` 与 `origin_mid_term_memory`
4. 基于旧 `mid_term_memory` 和可压缩 history 生成新摘要
5. 生成 `ContextCompressionResult`
6. 通过回调读取最新持久化会话状态并尝试 merge
7. merge 成功后保存新的 checkpoint
8. 使用 `id + lease_owner` 将压缩任务标记为 completed

这里要强调：

- 压缩任务归属于 `session_id + agent_name`
- 压缩结果不是完整 BaseAgentState
- 压缩结果是带原始快照边界的可合并结果
- 合并判断依赖 `origin_history` 与 `origin_mid_term_memory` 基线，而不是 checkpoint 版本号

## 6. 压缩结果结构

压缩结果表达为可合并结果，而不是状态覆盖。

最小结构建议如下：

```python
@dataclass(slots=True)
class ContextCompressionResult:
    """表示一次后台压缩生成的可合并结果。"""

    # 压缩结果是否已经成功合并回原始状态。
    merged: bool

    # 压缩前的原始中期记忆文本。
    origin_mid_term_memory: str

    # 压缩前的原始短期 history 快照。
    origin_history: list[RuntimeArtifact]

    # 本次压缩生成的中期记忆摘要文本。
    compressed_mid_term_memory: str

    # 压缩后仍保留在短期 history 中的 Runtime 产物列表。
    compressed_history: list[RuntimeArtifact]

    # 本次被吸收到摘要中的 history 产物数量。
    compressed_history_count: int
```

其中 `origin_history` 和 `origin_mid_term_memory` 是安全 merge 的边界。
当前合并要求最新 history 仍以 `origin_history` 为前缀；若前缀不匹配，说明压缩期间旧历史已经被其他流程重写，应放弃本次 merge，避免误删历史。

## 7. 写回合并语义

后台压缩写回不能要求“压缩开始版本”和“当前最新版本”完全一致。

压缩可能很慢，用户可能已经开启了下一轮 runtime run。此时最新版本不匹配是正常情况，不应直接丢弃压缩结果。

正确语义是 merge：

1. 加载任务对应 `session_id + agent_name` 的最新状态
2. 找到压缩任务对应的 running 记录
3. 判断最新 `history` 是否仍以 `origin_history` 为前缀
4. 判断最新 `mid_term_memory` 是否仍与 `origin_mid_term_memory` 一致
5. 将 `compressed_mid_term_memory` 合并进最新 `memory.mid_term_memory`
6. 用 `compressed_history + 压缩期间新增 history tail` 替换最新 history
7. 保存新的 BaseAgentState 快照或等价历史状态
8. 使用 `id + lease_owner` 将压缩任务标记为 completed

这里的判断重点不是版本号是否一致，而是：

- 压缩开始时的 history 前缀是否仍然保持一致
- 最新 mid_term_memory 是否仍与压缩开始时的基线一致
- 合并后的状态是否仍然满足数据不丢失原则

## 8. mid_term_memory 合并策略

如果写回时最新 `mid_term_memory` 没有变化，可以直接用压缩结果生成的新记忆文本替换。

如果最新 `mid_term_memory` 已经变化，不应直接覆盖。

推荐做法是：

1. 将最新 `mid_term_memory` 作为当前权威内容
2. 将压缩结果中的 `compressed_mid_term_memory` 作为新增摘要片段
3. 触发一次 merge/rewrite
4. 输出新的完整 `mid_term_memory`

第一阶段可以用 LLM 做 merge/rewrite。

后续如果 `mid_term_memory` 的章节结构稳定，可以逐步升级为章节级确定性合并。

## 9. 租约过期与失败处理

### 9.1 租约过期

`lease_expires_at` 用于避免 running 任务永久卡住。

当新的 runtime run 触发压缩判断时，如果发现已有 running 任务但租约已过期，可以允许重新创建或抢占。

重新创建有两种策略：

- 创建新的压缩任务
- 抢占旧压缩任务并刷新 `lease_owner` / `lease_expires_at`

当前 MySQL 实现选择“抢占旧压缩任务并刷新租约”，这样同一
`session_id + agent_name` 下不会积累多个 running 任务。

### 9.2 压缩失败

压缩失败不应影响主流程。

失败时建议：

- 将任务标记为 failed
- 记录 `error`
- 不修改 BaseAgentState
- 不删除 history
- 后续 runtime run 若仍然超过软限制，可以重新触发新任务

第一阶段不需要在任务模型中保存 `retry_count`。

## 10. 与同步压缩的区别

同步压缩和后台压缩服务不同目标。

同步压缩：

- 服务当前请求
- 超过 hard limit 时触发
- 必须在当前 build 返回前完成
- 可以直接修改当前运行态

后台压缩：

- 服务后续请求
- 超过 soft limit 时触发
- 不阻塞当前请求
- 必须基于稳定的 owner agent state 快照执行
- 必须通过持久化任务状态跨进程去重
- 写回时必须 merge 最新状态

## 11. 第一阶段落地顺序

建议按以下顺序实现：

1. 基于 RuntimeArtifact.id 前缀匹配定义 `ContextCompressionResult`
2. 后台压缩执行体只复制 owner agent state，不复制完整构建输入
3. 实现最小 merge 写回逻辑
4. 压缩成功后标记 completed，失败后标记 failed
5. 补充任务清理和观测能力

稳定 `RuntimeArtifact.id` 是当前安全 merge 的基础；没有它，后台压缩结果无法可靠确认自己覆盖了哪些原始 history 前缀。

## 12. 当前暂不处理的问题

以下问题第一阶段可以先不处理：

- `retry_count`
- 全局压缩任务队列实现
- 分布式 worker 调度系统
- 长期记忆压缩写回
- 多个不同类型压缩任务并行调度
- 压缩任务 observation 详情表

这些能力可以在后台压缩主语义稳定后再补。
