# 任务中断与恢复设计

## 1. 文档目标

本文描述 turtlemap 中“异步任务 request / response 机制”的目标设计。

该机制用于解决下面几类问题：

- 任务执行过程中需要用户确认，例如高风险工具调用前的人工审核。
- 任务执行过程中需要等待外部异步结果，例如后台工具、远程任务、三方系统回调。
- Runtime 执行过程中发生异常，需要把任务暂停下来，等待后续显式恢复。

本文同时描述当前基础实现和后续扩展边界。异常恢复、工具确认、异步工具等待、response 匹配和暂停任务上下文投影已形成基础闭环；一次暂停只挂载一个中断 request，复杂业务需要等待多少外部内容由 request 参数自行表达。

## 2. 核心原则

### 2.1 暂停不是失败

任务进入暂停状态表示当前任务暂时不能继续推进，但它不是失败，也不是普通完成。

`TaskStatus.PAUSED` 的语义是：

- 当前任务已经让出 Runtime 主循环。
- 当前 run 可以结束。
- 任务只能由匹配的 response 或系统内置恢复工具重新唤醒。
- 暂停原因和等待内容必须通过结构化 request 表达。

### 2.2 暂停对当前 run 等价于完成

任务切换到暂停状态后，对当前 Runtime run 来说等价于形成了一个稳定闭环。

Runtime 不继续持有完整执行产物，也不等待外部系统返回。业务层只需要保存：

- 已经输出给用户或前端的稳定内容。
- 当前暂停任务上的 `interruption_request`。
- 当前会话状态 checkpoint。

这样可以避免 SDK 把长时间异步等待、前端交互状态和远程任务生命周期全部压在 Runtime 内存里。

### 2.3 request / response 是恢复锚点

恢复不依赖自然语言推断，也不依赖 task_id 猜测。

每个中断请求必须有稳定的 `request_id`。外部响应必须携带同一个 `request_id`，Runtime 用它定位暂停任务中的 request，并把 response 写回 request。

### 2.4 history 只轻量感知中断

中断任务进入 history 时，不保存完整执行现场，不暴露工具内部过程，也不让 LLM 看到复杂中间产物。

history 由 `ContextBuildProvider` 根据暂停任务和 `interruption_request` 统一构建为轻量的 `input + assistant`：

```text
user:
{任务 start_input 对应的用户输入}

assistant:
<temporary_system_command>任务执行过程中发生中断，以下是中断信息</temporary_system_command>
任务 id: {task_id}
中断请求:
- request_id: {request_id}
  type: {request_type}
  reason: {reason}
```

这里的 `任务 id`、`中断原因`、展示文案等信息不应由 Runtime 手写，而应来自 request 的结构化字段，再由 `ContextBuildProvider` 统一渲染。

## 3. 数据模型

### 3.1 BaseProcessingTask

`BaseProcessingTask` 应增加单个中断请求：

```text
BaseProcessingTask
    task_id: str
    state: BaseTaskState
    start_input: Input | None
    interruption_request: InterruptionRequest | None
```

约束：

- 一次暂停只允许一个 active request。
- 需要等待多个外部内容时，由业务层把多个待办项聚合到 `request.params` 中。
- 模式层不表达并发 request，避免 Runtime 恢复条件和调度语义复杂化。
- request 被对应消费者消费完成后必须置空；异常恢复类 request 由 Runtime 唤醒时直接消费并置空。

### 3.2 InterruptionRequest

模型定义：

```text
InterruptionRequest
    request_id: str
    task_id: str
    type: str
    reason: str
    params: dict[str, object]
    response: InterruptionResponsePayload | None
```

字段语义：

- `request_id`：本次中断请求唯一标识，response 必须携带。
- `task_id`：当前 request 所属任务。
- `type`：请求类型，可理解为系统内置或业务扩展的 request 函数名。
- `reason`：中断原因，用于事件输出和 history 轻量摘要构造。
- `params`：当前 request 需要业务层或外部系统理解的参数。
- `response`：外部提交的完整响应载荷；为空表示仍在等待。

### 3.3 InterruptionResponse

模型定义：

```text
InterruptionResponse
    = InterruptionExceptionResponse
    | InterruptionAsyncToolResponse
```

约束：

- `InterruptionResponse` 是内置 request 类型对应的具体响应模型联合类型，不提供宽泛的 params 容器。
- response payload 不使用裸字典，应像 `UserInputPayload` 一样定义明确模型。
- `ObservableEvent.payload` 应通过 `register_field_type` 注册恢复为强类型 payload。

新增事件类型：

```text
EventType.INTERRUPTION_RESPONSE = "interruption_response"
```

新增 payload：

```text
InterruptionResponsePayload
    request_id: str
    request_type: str
    response: InterruptionResponse
```

注册关系：

```text
ObservableEvent.register_field_type(
    "payload",
    EventType.INTERRUPTION_RESPONSE,
)
```

## 4. 内置 request 类型

os 层第一阶段内置以下 request type：

```text
_os_exception_resume
_os_async_tool_request
```

### 4.1 _os_exception_resume

用于 Runtime run 过程中发生异常后的恢复请求。

流程：

1. os Runtime 捕获 run 异常。
2. 回退到 `last_session_state`。
3. 找到当前正在推进的 task。
4. 创建 `_os_exception_resume` request 并挂到 `task.interruption_request`。
5. 将 task 标记为 `PAUSED`。
6. 发送中断 request 事件。
7. checkpoint 当前稳定状态。
8. 当前 run 结束。

恢复时：

1. 业务层提交 `INTERRUPTION_RESPONSE`。
2. Runtime 根据 `request_id` 找到 paused task。
3. 将 response 写入对应 request。
4. 将 task 切回 `RUNNING`。
5. 清理 `_os_exception_resume` request。
6. 重新进入 Runtime 主流程。

### 4.2 _os_async_tool_request

用于异步工具执行等待外部结果。

流程：

1. ToolService 遇到异步工具 execution unit。
2. 创建 `_os_async_tool_request`。
3. 当前 execution unit 保持 `PENDING`，下次恢复后仍从该 unit 继续。
4. task 标记为 `PAUSED`。
5. 当前 run 结束。

恢复时：

1. Runtime 根据 `request_id` 写入 response。
2. task 切回 `RUNNING`。
3. ToolService 再次扫描到该 unit。
4. ToolService 优先检查 request response。
5. 若异步结果已返回，则生成 `ToolResult` 并推进 unit。
6. 若结果仍不可用，则再次暂停。

异步工具直接使用继承 `ToolResult` 的 `InterruptionAsyncToolResponse` 返回稳定结果，
无需再通过 `response.params.tool_result` 增加一层包装。

## 5. ToolMetadata 审核属性

为了支持 HITL，工具元信息需要能表达“执行前是否需要审核”。

第一阶段在 `ToolMetadata` 中只保留审核开关：

```text
requires_confirmation: bool = False
```

语义：

- `requires_confirmation=True` 表示 ToolService 在业务工具前插入一个异步 `HitlTool`。
- 用户可见的确认文案由展示层根据 `InterruptionRequest.params` 构造，不写入工具定义。
- 异步执行能力仍由现有 `execution_strategy` 表达。

后续若审核策略复杂化，再在业务层扩展独立模型，例如：

```text
ToolApprovalPolicy
    mode: str
    prompt: str
    risk_level: str
```

第一版不应过早引入复杂审核模型。

当前实现把审核统一建模为前置 `HitlTool`：它是普通异步内置工具，使用 `_os_async_tool_request` 与 `InterruptionAsyncToolResponse` 完成 request/response。`HitlTool` 将 `option` 解释为标准 `ToolResult`；同意后业务工具继续执行，拒绝时前置工具形成失败结果，业务工具读取该结果并停止执行。这样不再需要专用 HITL request type、response 模型或确认请求 id。

## 6. last_session_state

os 层需要维护 `last_session_state`。

语义：

- `last_session_state` 是最近一次成功 checkpoint 后的会话快照。
- 它只用于异常后回退。
- 只有 checkpoint 成功后才能更新它。
- 不能在内存状态刚修改后立即更新，否则异常回退会回到半成品状态。

异常中断流程必须基于 `last_session_state` 创建 request，而不是基于异常发生时的半中间态直接保存。

## 7. Runtime 恢复入口

Runtime run 开始时应优先识别 response 类输入。

流程：

1. 业务层传入 `ObservableEvent(event_type=INTERRUPTION_RESPONSE, payload=InterruptionResponsePayload(...))`。
2. Runtime 在当前 SessionState 中查找所有 paused task。
3. 在 paused task 的 `interruption_request` 中匹配 `request_id`。
4. 找到后写入 response。
5. 判断 task 是否满足恢复条件。
6. 若满足，task 状态改为 `RUNNING`。
7. 进入正常 Runtime 主循环。

约束：

- response 找不到 request，应抛出明确异常或返回业务可处理错误。
- response 不直接执行业务逻辑，只负责唤醒 task。
- ToolService / task state 才负责解释 response 的业务含义。

## 8. ContextBuildProvider 责任

`ContextBuildProvider` 负责根据暂停任务构造中断历史。

职责：

- 从 `BaseProcessingTask.start_input` 构造用户输入 history。
- 从 `BaseProcessingTask.interruption_request` 构造 assistant 中断摘要。
- 使用统一模板，不在 Runtime、ToolService 中分散拼接 prompt。
- 不暴露内部工具执行栈、异常堆栈、event bus 细节。

中断历史示例：

```text
<temporary_system_command>任务执行过程中发生中断，以下是中断信息</temporary_system_command>
任务 id: task:xxxx
中断请求:
- request_id: request:xxxx
  type: _os_async_tool_request
  reason: 工具 user_approval 正在异步执行
```

## 9. 事件输出

中断 request 应通过 event bus 通知业务层。

事件定义：

```text
InterruptedEvent
    interruption_type: InterruptionRequestType
    payload: InterruptionRequest
```

`payload` 直接展示挂载到暂停任务上的 `InterruptionRequest`。不同中断类型的
展示参数统一放在 `request.params` 中，例如人工确认选项使用 `options` 字段。

注意：

- event bus 事件用于通知和展示，并直接携带对应的 request 状态事实。
- task 上的 `interruption_request` 仍是恢复流程读取的权威状态。
- 业务层保存 request 时应以 task 状态为准，而不是反向从事件流推导。

## 10. 边界总结

kernel 负责：

- 维护 `TaskStatus.PAUSED` 调度语义。
- 保存 `BaseProcessingTask.interruption_request`。
- 基于 response 唤醒 paused task。

os Runtime 负责：

- 保存和更新 `last_session_state`。
- 捕获异常并创建 `_os_exception_resume` request。
- 发送中断 request 事件。

ToolService 负责：

- 基于 ToolMetadata 插入前置 HitlTool，并由它创建通用 async tool request。
- 基于异步工具策略创建 async tool request。
- 恢复后解释 request response，并推进 execution unit。

ContextBuildProvider 负责：

- 将 paused task 渲染为轻量 history。
- 保持中断历史格式统一。
- 避免 LLM 感知内部执行细节。

业务层负责：

- 展示 request。
- 收集 response。
- 保存已输出内容和 request。
- 通过 `INTERRUPTION_RESPONSE` 输入恢复任务。
