# Handoff 控制权转移设计

## 1. 文档目标

本文记录当前 turtlemap 已实现的 `handoff` 控制权转移机制。它以现有 Runtime、ToolService、上下文投影和消息拦截链路为准，定义 Agent 如何发起委派、目标 Agent 如何接管会话，以及何时自动返回父 Agent。

本文不描述早期方案中的 `HandoffState`、`complete_handoff` 或 `handoff_result` 回流模型。当前实现不依赖这些状态和控制工具：一次 handoff 由一次普通工具调用触发，由目标 Agent 最终消息中的继续标记决定是否保留控制权。

## 2. 核心结论

我将 `handoff` 定义为会话控制权的栈式转移，而不是“调用另一个 Agent 并取得一次结果”的工具调用。

```text
当前 Agent
  -- 调用 handoff 工具 -->
目标 Agent 接管后续会话输入
  -- 完成且未声明继续 -->
父 Agent 恢复控制权
```

它具有以下边界：

- `handoff` 会修改 `SessionState.agent_frames`，目标 Agent 成为当前会话 Owner；
- `handoff` 不复制 history，不为目标 Agent 创建私有会话副本；
- `handoff` 不等于 `agent_as_tool`。后者由当前 Agent 调用并在同一轮取得结果，不接管用户之后的多轮输入；
- 当前实现只支持后进先出的控制权栈。目标 Agent 结束时只能返回其直接父 Agent；
- 控制权是否保留由模型动态决定，但 Runtime 使用结构化运行参数读取决定，不解析展示给用户的自然语言。

## 3. 关键模型

### 3.1 Agent 声明与 handoff 工具

`BaseAgent.handoffs` 保存当前 Agent 可以委派到的下游 Agent。每个目标 Agent 必须提供 `AgentDescriptor`，它描述目标 Agent 对模型暴露的能力。

构造 Agent 时，Runtime 会将每个目标 Agent 转换成一个无参 `ExecutableTool`：

```text
tool id:       _handoff_{target_agent_name}
function name: _handoff_{target_agent_name}
input:         EmptyToolInputModel
```

`_handoff_` 是稳定前缀。它既用于识别模型生成的 handoff tool call，也让普通工具执行链路能够在不依赖 Agent 业务类型的情况下识别控制权转移。

这个工具的普通 `call` 实现会抛出异常。真正的 handoff 只能由 os 层 `ToolService` 在 Runtime 执行上下文中解释；它不能被当作一般 Python 工具直接调用。

### 3.2 AgentFrameChange

`BaseAgentFrameChange` 是跨 kernel 和 os 的稳定控制载荷：

```text
AgentFrameChange
    source: str
    target: str
    type: PUSH | POP
    reason: HANDOFF | HANDOFF_RETURN
```

- 发起 handoff 时，os 层构造 `PUSH + HANDOFF`；
- subagent 完成且返回父 Agent 时，os 层构造 `POP + HANDOFF_RETURN`；
- `BaseProcessingTask.agent_frame_change` 挂载当前完成任务需要执行的变更。`None` 表示任务结束后保持当前控制权。

`kernel` 只执行已经构造好的变更，不解释 handoff 工具前缀、LLM 运行参数或展示内容。

## 4. 发起 handoff

### 4.1 工具暴露与防循环

每轮构建工具集合时，`ToolService` 会读取 `session_state.agent_frames`：

- 已经位于当前控制权栈中的 Agent，不再作为 handoff 工具暴露给模型；
- 被过滤时记录 warning，包含目标 Agent、工具 id 与当前 frame 栈；
- 这样可以防止 `A -> B -> A` 等循环委派，而无需在模型提示词中依赖模型自我约束。

### 4.2 工具调用处理

当前 Agent 的 LLM 响应出现 handoff tool call 后，`ToolService` 按以下规则处理：

1. 将对应调用构造成 `ToolCallExecutionUnit`；
2. 发布普通 `ToolCallEvent`，使事件流仍能完整观测工具调用；
3. 生成成功 `ToolResult`，正文使用来源与目标 Agent 的对外展示名称说明控制权转移；
4. 在 `ToolResult.raw_data` 中保存 `AgentFrameChange(PUSH, HANDOFF)`；
5. 将该变更同步写入 `ToolCallExecutionResult.handoff`；
6. 停止执行同一 assistant message 中位于 handoff 之后的所有 tool call，并记录 warning；
7. 不追加工具 loop 的 continuation LLM 调用。

第 6、7 点很关键。handoff 一旦成立，来源 Agent 已不再拥有本轮后续控制权；继续执行后续工具或要求来源 Agent 再生成一次回复都会让会话主体和工具归属变得不确定。

### 4.3 任务完成时提交控制权变更

工具链完成后，kernel 先按正常规则把本轮工具过程写入会话 history。任务仍处于 `COMPLETED` 时，才调用 os 层的任务完成 hook。

os 层从 `ToolState` 最后一个执行单元的结果读取 `handoff`，并把它写入 `task.agent_frame_change`。随后 kernel：

1. 校验当前 frame 栈顶 Agent 与 `frame_change.source` 一致；
2. 将目标 Agent 作为新的 `AgentFrame` 压入栈顶，记录其 `from_agent_name`；
3. 克隆来源任务的 `start_input`，生成新的 `input_id`，并将旧 id 记录为 `origin_input_id`；
4. 将该输入内事件的来源标记为 `HANDOFF`，重新压入会话输入队列；
5. 发布 Agent frame 变更事件；
6. 移除已完成的来源任务。

因此目标 Agent 处理的是同一条用户原始问题，而不是 handoff 工具结果本身。原输入会以新的输入包重新进入 Runtime，保证任务、事件和持久化链路仍遵循统一的输入驱动模型。

## 5. 目标 Agent 的上下文

### 5.1 会话 history 与 Agent 视角

history 属于 Session，不属于 Agent。handoff 后目标 Agent 从共享 history、共享 memory、自己的系统定义和当前可用工具共同构建上下文。

每个 `RuntimeArtifact` 都记录 `owner_agent_name`。投影时：

- 当前目标 Agent 自己产生的历史，保留原生 `assistant`、`tool` 协议；
- 其他 Agent 的连续历史按所属 Agent 聚合为 `Group Input`；
- `Group Input` 被注入目标 Agent 当前任务第一个 user input 的 `Task Context`，而不是另起一条 user role；
- 外部 Agent 的工具调用以 XML 描述，不能诱导目标 Agent 将其当成自己可直接续接的原生 tool call。

这保证目标 Agent 能理解前序 Agent 已经完成的会话过程，同时不会把前序 Agent 的工具协议误认为自己的执行历史。

### 5.2 来源 Agent 工具链闭合

handoff 后来源 Agent 不会再执行 continuation LLM 调用，但其工具调用仍必须在历史投影中闭合。`ContextProjector` 会投影：

1. 来源 Agent 的 assistant tool call；
2. handoff 的 tool result；
3. 一条携带“控制权从来源转交给目标”的 assistant 消息。

第 3 条仅用于闭合来源 Agent 的原生工具链，不代表新的业务事实或一次额外模型调用。

## 6. 保持或返回控制权

### 6.1 继续标记

当当前 Agent 位于非根 frame 时，系统指令会要求模型：只有当前委派任务仍需要继续推进时，才在最终输出追加 `<#CONTINUE#>`。

默认 `AgentInterceptor` 负责这个标记的流式处理：

- 若正文尾部出现可能尚未完整的标记前缀，先截流，避免展示层看到半个控制标记；
- 标记完整后，从 `display` 通道删除标记；
- `context` 通道保留原始标记，使后续模型上下文仍能看到真实控制语义；
- 将 `has_continue_tag=True` 写入 LLM 消息的 `runtime_params`。

展示层不会看到控制标记，Runtime 也不需要从最终文案重新搜索字符串。

### 6.2 任务完成后的判断

每个任务完成时，os 层统一生成 `task.agent_frame_change`：

1. 若工具任务结果已包含 handoff 变更，优先使用该 `PUSH`；
2. 否则，若当前 Agent 不是 subagent，保持当前 frame；
3. 若当前 Agent 是 subagent，读取本任务最终 `LLMMessage`：
   - `MessageState` 使用完成的 assistant message；
   - `ToolState` 只在最后一个执行单元是 continuation LLM 调用时使用其 message；
4. 最终消息不存在，或 `runtime_params.has_continue_tag` 为 `True` 时，保持当前 frame；
5. 否则构造 `POP + HANDOFF_RETURN`，目标为当前 frame 的直接父 Agent。

kernel 执行 `POP` 后会发布 `AgentFrameChangeEvent`。来源任务和返回任务均会以各自 task id 进入事件流，展示层或业务侧可以据此绘制控制权变更。

## 7. 事件、持久化与恢复边界

handoff 复用既有 Runtime 生命周期，不创建专用的 handoff task 或 handoff result 事件：

- `ToolCallEvent`、`ToolResultEvent` 继续表达 handoff 工具的执行过程；
- `AgentFrameChangeEvent` 表达已实际执行的 `PUSH` 或 `POP`；
- frame 变更和重新入队的 handoff 输入都写入 `SessionState`，随正常 Runtime checkpoint 持久化；
- 未完成的目标 Agent 任务就是普通 `ProcessingTask`，恢复时仍通过任务和输入队列继续推进；
- `AgentFrameChange` 在任务完成后才执行，因此不会持久化一个“工具已声明 handoff、但 frame 尚未改变”的独立中间协议。

## 8. 约束与后续边界

当前 handoff 机制刻意保持以下约束：

- 只支持显式声明的 Agent 图；目标必须位于来源 Agent 的 `handoffs` 中；
- 不允许 handoff 到当前 frame 栈已存在的 Agent；
- 只支持栈式返回，不支持跳过中间 Agent 直接返回任意祖先；
- 不把 handoff 当作“生成结果的工具”。需要单轮委派和聚合结果时，应实现 `agent_as_tool` 或专用 `ExecutionUnit`；
- 尚未实现与 handoff 无关的显式 `takeover`；
- `<#CONTINUE#>` 是当前控制协议。未来若引入结构化 completion 指令，可以替换标记产生方式，但 Runtime 应继续消费稳定运行参数，而不是直接解析展示文本。

## 9. 完整时序

```text
用户输入
  -> 来源 Agent 生成 handoff tool call
  -> ToolService 识别 _handoff_{target}
  -> ToolResult 携带 PUSH/HANDOFF AgentFrameChange
  -> 来源任务完成
  -> kernel push target frame
  -> 克隆原始 input 并以 HANDOFF 来源重新入队
  -> 目标 Agent 接收 Group Input + 原始用户任务
  -> 目标 Agent 生成回复
      -> 含 <#CONTINUE#>：保留 target frame
      -> 不含标记：POP/HANDOFF_RETURN，恢复父 Agent frame
```

这条链路的关键不是“谁调用了谁”，而是 Runtime 始终能够明确回答：当前由哪个 Agent 接收下一条输入、该 Agent 看到哪些会话材料、以及何时以什么原因发生了控制权变更。
