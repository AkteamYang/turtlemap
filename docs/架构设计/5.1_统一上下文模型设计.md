# 统一上下文模型设计

## 1. 文档目标

统一上下文模型是 turtlemap 中 Agent 全面感知运行期信息的基础设施。它不只服务于多 Agent 协作，也不等同于一组传给 LLM 的 `messages`：会话历史、记忆、当前任务、工具过程、系统控制信息、外部注入内容和环境信息，都先作为 Runtime 中有语义的结构化材料存在，再按当前 Agent、任务与策略投影为 LLM 可消费的上下文。

这套模型解决的是“当前 Agent 应当感知什么、这些信息以什么边界进入推理”的问题。多 Agent、handoff、记忆、工具恢复、外部事件注入与上下文压缩，都是统一上下文模型之上的不同应用。

## 2. 核心结论

> 上下文是 Runtime 对会话及当前运行现场的统一信息模型，而不是 Agent 私有的聊天记录，也不是对原生 LLM 消息格式的简单堆叠。

原生 LLM 消息只有 `system`、`user`、`assistant`、`tool` 等有限角色，难以准确表达“其他 Agent 已执行的工具过程”“当前任务约束”“等待恢复的任务”“控制权变化”“外部系统插入的信息”等 Runtime 事实。若在信息产生时就强行压平为 LLM message，会丢失来源、时效、可见范围与控制语义，后续只能依赖字符串约定回推。

因此，统一上下文模型遵循以下原则：

- Runtime 内部保留信息的原始语义、来源和生命周期；
- 仅在构建 LLM 请求时，按当前场景选择合适的消息角色或结构化区块；
- 当前 Agent、任务、工具集合、可见范围和 token 预算只影响投影，不改变稳定信息的归属；
- 多 Agent 不复制或合并聊天副本，而是在同一会话信息模型上形成不同视角。

## 3. 信息来源与状态归属

### 3.1 Session Context

`SessionState` 承接跨任务、跨 Agent 持续存在的会话材料，至少包括：

- 按顺序保存的 `RuntimeArtifact` history；
- 会话级 `MemoryView`，包括中期摘要与本轮加载的长期记忆视图；
- 输入队列、Agent frame 栈及可恢复任务索引等会话控制状态。

会话 history 是稳定过程事实的权威来源。用户输入、最终 assistant 消息、工具调用与结果、Agent frame 变化等都可以以 artifact 保留；它们是否、以及如何进入某次 LLM 调用，则由投影层决定。

`MemoryView` 同样属于会话：

- `mid_term_memory` 承接会话摘要和阶段性沉淀；
- `long_term_memory` 的权威存储可在用户、租户或项目范围，但当前加载结果以会话视图参与构建；
- 有可见范围的私有材料应在投影前完成分组，不在每个 AgentState 中复制一份。

### 3.2 Agent 与 Task Context

`BaseAgentState` 只保存 Agent 在当前会话中的运行现场，例如该 Agent 的任务集合及不可从公共 history 推导的状态。它不拥有独立 history 或会话摘要。

`ProcessingTask` 表示一次处理过程，承接：

- `start_input` 与当前任务约束；
- 执行单元、工具调用关联、中断与恢复状态；
- 当前任务新增的产物和待处理事件。

Agent Definition、系统提示、能力描述和工具集合是当前 Agent 的运行时定义。它们与 Session Context 一起构成投影输入，但不被误写为会话聊天历史。

### 3.3 外部与控制信息

统一上下文模型还需要表达不属于普通聊天轮次的信息，例如：

- 外部系统注入的事件、业务数据与任务约束；
- 当前时间等运行环境信息；
- 工具结果的时效性、暂停任务与恢复提示；
- Agent handoff、控制权归还等会话控制事实；
- 来自其他 Agent 的消息、工具调用及工具结果。

这些材料保留结构化语义，避免伪装成当前 Agent 自己发出的 `assistant` 或 `tool` 消息。

## 4. 上下文投影

`ContextBuildProvider` 基于会话状态和当前运行现场构建 `ContextSource`。它保存本轮构建所需的完整原材料；`ContextProjector` 再将其投影为模型消息。进入模型的文本上下文固定为四层：`System`、`Memory`、`History` 与 `Task Input`。工具 schema 随请求一并提供，但不混入这四层文本上下文。

```text
System
  + Memory
  + History
  + Task Input
      ├── User Input
      ├── Task Constraints
      └── Task Context
          └── Group Input
  = LLM Context Projection
```

投影是一次性的 LLM 输入视图，不是新的持久化副本。四层的职责边界如下：

1. `System`：Framework Instructions 与当前 Agent Definition，定义当前 Agent 的身份、能力边界和通用运行规则；
2. `Memory`：会话摘要与加载的长期记忆视图；
3. `History`：已稳定的历史用户输入、assistant 消息与工具过程。普通历史输入保持纯 `User Input`；带有 `Group Input` 的历史输入在投影时恢复为简化版 `Task Input`；
4. `Task Input`：本轮任务的即时输入概念，由 `User Input`、`Task Constraints` 与 `Task Context` 组成。

`Task Context` 承载辅助理解当前任务、但不等同于用户直接要求的信息，例如环境信息、恢复提示、外部业务材料和控制事实。凡是不属于当前 Agent 自己的原生执行历史、但需要在本轮让其感知的信息，统一通过 `Task Context` 中的 `Group Input` 表达。

`Task Input` 只用于描述输入的整体结构，不会作为固定标题直接渲染到 prompt。实际消息只按内容选择性呈现 `User Input`、`Task Constraints` 与 `Task Context` 区块。

`Task Input` 只是在当前构建期成立的入口结构。输入稳定进入 history 后，通常回归为纯 `User Input`，不携带系统结构；`Task Constraints` 也只属于本轮运行规则，不作为 history 内容保存。只有该轮存在 `Group Input` 时，history 投影才恢复为简化版 `Task Input`，其中仅保留 `User Input` 与 `Task Context / Group Input`，以维持外部会话过程与该用户输入的关联。

当前可用工具由工具服务筛选后作为独立 tool schema 随请求提供；它影响模型可执行的能力边界，但不改变四层文本上下文的结构。

同一份 Session Context 可以对不同 Agent 形成不同投影：目标 Agent 会附带自己的能力定义和工具集合，当前任务决定输入区块，token 策略决定历史保留范围。差异发生在投影层，不需要维护多份会话事实。

### 4.1 信息到 LLM 表达的映射

| Runtime 信息 | 内部承载 | LLM 投影方式 |
| --- | --- | --- |
| 当前 Agent 自己的连续 assistant 消息与工具过程 | `RuntimeArtifact` history | 原生 `assistant`、`tool` 消息 |
| 会话记忆 | `MemoryView` | 独立的 Memory Context 区块 |
| 当前用户输入 | 输入事件 | 当前 `user` 消息中的 `User Input` 区块 |
| 不带 `Group Input` 的历史用户输入 | `RuntimeArtifact` history | 纯 `user` 消息 |
| 带 `Group Input` 的历史用户输入 | `RuntimeArtifact` history | 简化输入结构，仅含 `User Input` 与 `Task Context / Group Input` |
| 当前任务约束 | `ProcessingTask` 与运行策略 | 当前 `user` 消息中的 `Task Constraints` 区块 |
| 环境、恢复提示与外部业务材料 | Runtime 与任务现场 | 当前 `user` 消息中的 `Task Context` 区块 |
| 其他 Agent 产生的过程 | history 中的 artifact | `Task Context` 内的 `Group Input` XML |
| Agent frame 变化 | `AgentFrameChange` artifact | 面向相关接收者的自然语言消息 |
| 当前可调用能力 | 工具服务筛选结果 | LLM tool schema |

这里的关键不是让每类信息都生成一条 LLM message，而是让它以不破坏协议语义的形式可被当前 Agent 感知。例如，其他 Agent 的 `<tool_call>` 只描述已经发生的外部过程，不会被模型误认为当前 Agent 自己必须续接的原生 tool call。

### 4.2 工具过程与时效性

工具调用和工具结果属于会话 Runtime 产物，但不代表每个 Agent 都应看到完整原始协议。

- 当前 Agent 自己的历史可按原生工具协议投影；工具不可用时可折叠中间过程，只保留本轮输入与最终结论；
- 工具结果过期时，保留调用关联与过期状态，移除过期正文，避免将旧结果当作当前事实；
- 其他 Agent 的工具过程以 `Group Input` 说明性结构投影，不构成当前 Agent 的原生 tool call；
- 需要跨 Agent 长期复用的业务事实，应由最终回复、记忆或外部权威数据源表达，而不是依赖某段工具原始结果。

裁剪与时效治理属于投影策略，不是对 Session Context 的简单删除。

### 4.3 Group Input

`Group Input` 是统一上下文模型对“外部会话过程”的一种投影格式。它表示自当前 Agent 上一次执行以来，尚未由当前 Agent 处理的相关信息，作为最近任务输入 `Task Context` 的组成部分出现，不单独生成新的 `user` role，也不作为独立 history 节点保存。带有 `Group Input` 的历史用户输入在再次投影时，会恢复为只包含 `User Input` 与 `Task Context / Group Input` 的简化版 `Task Input`；不带 `Group Input` 的历史输入则保持纯用户输入。

```xml
<group_input>
  <message actor="User">
    用户输入内容
  </message>
  <message actor="research_agent">
    其他 Agent 的回复内容
  </message>
  <tool_call actor="research_agent" name="query_metrics" id="call:metrics">
    {"metric":"latency"}
  </tool_call>
  <tool_result call_id="call:metrics">
    工具结果内容或过期标记
  </tool_result>
</group_input>
```

容器中的元素按会话原始顺序排列，正文与属性遵循 XML 转义规则。它既保留消息来源、调用关联和时效信息，又避免把外部 Agent 的过程伪装成当前 Agent 的执行历史。当携带它的用户输入进入 history 时，容器仍与该输入关联，但不会被拆成独立的 history 记录；后续构建 history 时再按需恢复到简化版 `Task Input`。

## 5. 多 Agent 是统一模型上的协作视角

多 Agent 协作不是另一套上下文系统，而是不同 Agent 在同一 Session Context 上执行不同投影。

### 5.1 Handoff

`handoff` 表示将明确任务暂时交给目标 Agent。控制权切换不会复制 history 或 memory：目标 Agent 接收空的 `HANDOFF` 输入，由 `Group Input` 感知原始用户问题、前序回复和工具过程，并叠加自己的 Agent Definition、工具与任务约束。

当前实现中：

1. 来源 Agent 调用 handoff 工具，Runtime push 目标 Agent frame；
2. 目标 Agent 通过 `Group Input` 接续会话，而不重复接收原始用户文本；
3. 目标 Agent 输出 `<#CONTINUE#>` 时保留当前控制权，等待下一轮输入；
4. 目标 Agent 未输出标记时自动 pop 回直接父 Agent，但不额外触发父 Agent 回复；
5. 当前问题超出目标 Agent 能力范围时，可调用 `_handoff_return` 显式归还控制权并立即唤起父 Agent。

控制流细节以[Handoff 控制权转移设计](./5.0_Handoff控制权转移设计.md)为准。

### 5.2 Agent Frame 变化的可见性

Agent frame 变化首先是 Runtime 控制事实，而不是用户对话文本。投影时会根据接收者决定是否生成自然语言提示：`PUSH + HANDOFF` 需要补 assistant 消息闭合来源 Agent 的工具调用链；子 Agent 自然完成触发的 `POP + HANDOFF_RETURN` 前已有最终回复，不再补消息，避免形成两个连续 assistant；`_handoff_return` 工具触发的 `POP + HANDOFF_RETURN_TOOL` 没有后续 LLM 生成，需补 assistant 消息闭合工具链。无论变更类型如何，其他 Agent 在 `Group Input` 中都会收到控制权状态提示。

这种差异正是统一上下文模型的价值：一份控制事实可以因接收视角不同而采用不同表达，而不需要在底层复制或篡改历史。

## 6. 压缩、记忆与恢复

压缩和记忆面向 Session Context，而不是某个 Agent 的局部聊天副本：

- 中期摘要覆盖整条会话，压缩结果回写 SessionState；
- Agent 切换不会生成新的摘要副本；
- 后台压缩按 `session_id` 收敛并发，避免多个 Agent 为同一历史生成相互冲突的摘要；
- 不同 Agent 可因任务、工具和 token 预算得到不同历史长度，但共享同一份摘要与稳定 history；
- 暂停、恢复与输入队列信息作为任务和会话控制材料投影，避免被压扁为普通对话文本。

私有材料在进入摘要或 projection 前必须按可见范围处理。公共摘要不能吸收 Agent 私有记忆、任务私有工具结果或未授权的外部材料。

## 7. 实现边界

- 不为每个 Agent 保存独立 history、摘要副本或独立压缩结果；
- 不把所有 Runtime 信息直接塞进原生 LLM message；
- 不将其他 Agent 的工具调用伪装成当前 Agent 的 tool protocol；
- 不把工具原始结果当作跨 Agent 的长期事实；
- 不让上下文投影反向改变稳定 Session Context 的所有权；
- 不用字符串约定替代任务、会话控制和时效状态的结构化表达。

## 8. 当前结论

统一上下文模型使 Agent 能在不受原生 LLM 消息格式限制的前提下，感知会话历史、记忆、任务、工具、外部事件和协作过程。LLM 消息只是最终投影载体，不是 Runtime 内部唯一的信息模型。

在这个基础上，单 Agent 对话、多 Agent handoff、工具恢复、记忆压缩与外部信息注入都使用同一套归属和投影规则；后续扩展新的信息来源时，只需要定义其 Runtime 语义、可见范围和投影策略，而不需要再发明一套 Agent 专用 history。
